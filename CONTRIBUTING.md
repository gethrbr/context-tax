# Contributing

Issues and pull requests are welcome.

## Running it

```bash
npm install
npm test
npm run dev            # runs the CLI from source
```

Before opening a pull request:

```bash
npm run typecheck      # tsc --noEmit, strict
npm run lint           # eslint; no-explicit-any is an error here, not a warning
npm test
npm run build
```

CI runs typecheck and lint once on Node 22, because their output does not vary by Node version, and
runs the tests and the build on Node 18, 20 and 22. Each matrix leg then packs the tarball, installs
it into a clean directory and runs it, because a build that compiles is not evidence that the thing
people install works.

## The bar for a change

This package makes claims about somebody's machine and then offers to edit their settings, so the
standards are about what it is allowed to say.

**A finding the tool cannot defend line by line is a bug in the tool.** Every bug found so far was
found by running it against real projects and reading each finding by hand, not by reading the code.
If you change a verdict, run the tool against several real projects and check the output yourself.

**No claim without its denominator.** "Unused" is not a finding; "0 calls in 135 sessions since it
was configured" is. If the window cannot be established, the verdict is withheld or downgraded to an
upper bound, out loud.

**Tests are mutation-checked.** Put the bug back and watch the test fail before you trust it. A test
that has never been seen to fail is not evidence of anything. Two real bugs here lived in branches
that had full green suites around them and no coverage of the branch itself.

**Zero runtime dependencies.** This is a hard constraint, not a preference. `npx context-tax` should
stay a single fast download.

**Nothing leaves the machine.** No telemetry, no model calls, no new network destinations beyond the
MCP servers the user already configured.

**No real machine data anywhere.** Not in tests, not in fixtures, not in the README. Every server
name, path and token count in this repository is invented. The example screens in the README are
generated by feeding a fabricated fixture through the real renderers, so they stay accurate without
anybody's actual configuration being the source. If you are adding an example, generate it the same
way rather than pasting your own output.

## Style

- TypeScript, `strict`, no `any`.
- Comments explain *why*, especially where a number could be misread. The existing files are the
  reference for tone.

## Releasing

Maintainers only. The workflow publishes on a published GitHub release, never on a push.

1. Bump `version` in `package.json`.
2. Add the section to `CHANGELOG.md`.
3. Merge that through a pull request like anything else.
4. Tag and publish a GitHub release as `v<version>`.

`prepublishOnly` runs typecheck, lint, the full suite and the build before the tarball is made, so a
release cannot be cut from a red tree. The workflow separately asserts that the tag matches the
manifest version: a release tagged `v0.2.0` that publishes `0.1.0` is worse than a failed release,
because it succeeds quietly and the tag lies.

Tags matching `v*` are protected against deletion and force-push, so a published version's tag
always points at what was published.
